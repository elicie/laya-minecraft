# 창고 건설 흐름과 검증

사용자가 “창고를 만들어 줘”라는 목표 하나를 등록하면 아래 흐름을 이어서 수행합니다. 좌표를 지정하지 않으면 실제 봇 위치를 기준으로 주변 부지를 탐색합니다. 취소한 과거 목표를 되살리지 않으며, 새 지시는 별도 목표로 등록합니다.

| 단계 | 수행과 완료 근거 | 이번 점검에서 보완한 부분 |
| --- | --- | --- |
| 목표 해석·계획 | 설계도와 버전을 고정하고, 명시 좌표가 없으면 주변 부지 탐색 작업을 배정 | 기본 설계도도 주변 탐색을 기본으로 연결 |
| 부지 확보 | 전체 기초·건물 공간·출입로를 실제 블록으로 관측 | 기존 구현 사용. 기존 건물·위험 지형·현재 발판을 보호 |
| 부지 정리 | 필요한 경우 중앙에서 승인하고 예약한 얕은 자연 지형과 풀만 변경, 실제 도착과 지형을 재검증 | 기존 구현 사용. 공용 라이브러리의 자동 다리·탑 설치는 비활성화 |
| 재료·도구 준비 | 실제 주변 자원을 채집하고 작업대·곡괭이·제련기 등 필요한 제작 경로를 재귀적으로 준비 | 충돌 없는 안전한 풀의 통행, 관측된 목재 연료와 자원 접근 조건 보완. 작은 설계도는 슬롯 여유를 확인해 지상에서 재료를 먼저 준비 |
| 건설 | 이미 설계와 일치하는 블록은 유지하고 부족한 블록만 설치. 문·가구·지붕과 출구도 실제 상태로 검증 | 실행 중 재료 확보·제작·건설과 차단 사유를 UI에 표시 |
| 창고 확인·연결 | 건설 이후 별도 작업에서 전체 건물 재관측과 실제 상자 열기·내용 관측을 수행 | 이 증거가 확인된 후 목표 완료. 공동 창고가 없으면 새 상자를 자동 등록. 상자 관측·입출고가 같은 접근 기준을 사용 |
| 보존·후속 작업 | 완료 목표·검증한 상자·공동 창고 설정을 저장하고 이후 채집에서 건물 블록을 보호 | 완료한 검증 창고의 바닥 등도 자원 채굴 후보에서 제외. 완료한 일회성 목표의 취소 요청도 증거와 보호를 유지 |

이미 공동 창고가 설정되어 있으면 기존 설정을 유지하고 새 건물의 검증한 상자 위치를 목표에 기록합니다. 상자가 없는 사용자 정의 설계도는 건물만 완료하며 공동 창고로 연결하지 않습니다. 창고 없이 등록한 기존 인벤토리 수집 목표는 원래 완료 기준을 유지합니다.

재료·이동·안전 조건이 충족되지 않으면 진행과 예산을 보존하고 실제 조건 변화를 기다립니다. 대기나 부지 방문만으로 건물 또는 창고가 완료됐다고 판단하지 않습니다.

사용자 건축은 기본적으로 재료 확보 후 실제 작업 지점으로 돌아오는 제한된 원정을 사용합니다. `materialExpedition: false`를 명시하면 기존 설정을 유지합니다. 지형 정리·접근로 정리·창고 등록 단계에는 이 기본값을 적용하지 않으며, 이미 소비한 탐색 횟수와 시간은 보존합니다. 자원 접근 계획의 흙 발판에 자연적으로 잔디가 자라도 같은 지지체로 재관측하며, 일반 건물의 블록 완료 기준은 그대로 적용합니다.

관제의 재고는 현재 연결의 실제 상자 관측을 우선 표시합니다. 새 관측이 없으면 같은 월드·차원·창고의 보존된 작업 결과에서 마지막 확인 수량과 시각을 표시하고 오래된 정보로 표시합니다. 이 표시용 과거 재고는 작업 완료나 제작 재료의 근거로 사용하지 않습니다. 대기 중 자동 재고 확인은 상자 주변 8블록 안에서 수행하며, 먼 거점 복귀는 배정받은 작업이 관측한 짧은 구간을 따라 진행합니다.

장비 없는 식량 탐색은 해질녘에 진행을 보존하고 야간 대피를 시도합니다. 먼 창고 접근이 문 통과 전에 실패하면 가까운 자연 흙 은신처를 확인합니다. 이미 창고 안에서 문을 닫고 대기 중이거나 문 통과를 시작한 상태는 해당 출입 절차를 보존합니다. 이 동작은 실행 코드이며, 게임 기록 저장으로 모델 가중치가 학습되지는 않습니다.

옆굴을 만들 지형이 없으면 현재 발판 아래의 자연 흙 세 칸과 기존 바닥·옆벽을 전부 관측한 경우에만 수직 은신처를 만듭니다. 보호 영역·낙하 지형·빈 지지체·다른 플레이어가 있는 위치는 거부합니다. 자체 흙 드롭 세 개를 모두 회수하고 입구를 막으며, 낮과 안전한 출구를 확인한 뒤 공개 점프·설치 API로 원래 지면에 올라와 세 칸을 흙으로 복원합니다. 시작 인벤토리나 외부 자재가 필요하지 않습니다. 닫힌 은신처 체크포인트는 재접속해도 유지합니다.

연속 운영 측정은 `python3 scripts/monitor-fleet-run.py <run-name>`으로 시작합니다. 기본 대상은 활성화한 운영 봇 전체이며 `--bots LayaTest01 LayaBaseMonitor`처럼 이름을 명시하면 해당 집단만 측정합니다. 시작 기록에 실제 대상과 세션을 고정하고 읽기 전용 SQLite 관측으로 72,000 월드 틱을 기록합니다. 재시작·단절·소스 변경·오래된 보고는 측정을 무효화합니다. 두 대의 기록을 여섯 대의 검증으로 보고하지 않습니다. 사망과 정체를 기록하며 시간 충족만으로 무사망이나 건축 완공을 뜻하지 않습니다. `scripts/audit-base-decisions.py <output.json> --after <unix-ms>`는 실제 모델 선택과 실행 결과를 연결해 검토용으로 내보내며 정답 라벨이나 학습 완료를 생성하지 않습니다.

경비를 추가해도 장비가 자동 지급되지는 않습니다. 실제 인벤토리에 검이나 도끼가 있는 봇만 지원 전투를 배정받습니다. 무기 없는 경비는 가까운 동료 수와 관계없이 적과 거리를 확보하며, 다른 봇의 지원 요청이 자신의 장비 제작을 끊지 않습니다. 경비 위치 유지와 건축·식량·입고 목표의 완료는 각각 실제 관측으로 확인합니다.

남은 재료가 256개 이하인 `cabin`·`house`·`warehouse`는 실제 빈 슬롯과 묶음 여유를 확인하고, 중간 원료·도구용 4칸도 남을 때 건설 전에 필요한 완성 재료를 준비합니다. 가구·유리·문·횃불을 먼저 제작하고 조약돌·판자를 마지막에 확보하므로 중간 제작이 건축용 판자를 소비해도 남은 수량을 다시 확인합니다. 준비 후 실제 입구로 복귀해 부지를 재검증합니다.

전체 재료를 수용하기 어려운 설계는 실제 남은 블록 기준으로 최대 16개씩 준비합니다. 보유한 재료를 먼저 사용하며, 문·침대의 자동 생성되는 두 칸은 아이템 한 개로 계산합니다. 일부만 확보한 조건 대기는 확인된 재고부터 설치하되 부족 사유와 소진한 탐색 예산을 보존합니다. 설치나 제작 효과가 불확실한 오류는 계속 진행하지 않습니다.

건물 안에서 바닥보다 한 칸 높은 상자는 기존 접근 반경 2 안에 걸을 수 있는 경로 노드가 없을 수 있습니다. 관측·등록·입출고는 반경 3의 안전한 접근 위치를 찾고, 실제 상자 상태와 눈에서 상자 중심까지 4.5블록 이내인지 확인한 뒤 공개 API로 엽니다. 실제 열기와 양쪽 물자 수량 변화로 성공을 확인하며, 접근을 위해 벽을 부수거나 임시 블록을 설치하지 않습니다.

## 실제 검증 범위

`tests/warehouse-bootstrap.live.test.ts`는 별도 API, 실제 fork 워커와 `minecraft-laya-validation` 서버의 `127.0.0.1:25566`을 사용합니다. 관리 명령을 실행하기 전에 Docker의 공개 포트를 검사합니다.

기본 창고 목표를 자연어 해석 API로 등록하며, 시작 인벤토리는 비어 있습니다. 검증 구역에는 풀로 덮인 지면과 실제 원목·돌·모래·석탄 원천 블록을 준비합니다. 봇에게 도구나 건설 재료를 지급하지 않습니다. 목표 완료 시 실제 136개 설계 블록을 서버 명령으로도 각각 확인하고, 실제 상자 열기 결과와 공동 창고 등록을 검사합니다. 후속 원목 4개 수집 목표가 새 창고에 입고되어 완료되고 SQLite에 창고와 완료 목표가 저장되는 것까지 확인합니다.

이 테스트는 준비한 자연 자원이 있는 주간 구역에서 최초 체력·허기를 회복한 조건의 검증입니다. 임의의 생존 월드나 야간 위협 속에서 항상 건설을 마친다는 보장은 아니며, Laya 모델 가중치 학습과도 별개입니다. 실제 실행 결과는 `docs/validation.md`에 기록합니다.

개인 장비의 재료는 수집 목표의 `completionLocation: "inventory"`와 `requiredBotId`로 특정 봇의 실제 인벤토리만 검사할 수 있습니다. 공동 창고가 있어도 창고 관측·입고를 기다리지 않으며 다른 봇의 보유량은 개인 목표에 합산하지 않습니다. `requiredBotId`는 제작·경비 등에도 배정을 제한합니다. `preferredBotId`의 기존 우선 배정 방식은 유지합니다.
