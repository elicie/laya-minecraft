# 구현 검증

2026-10-13 기준으로 소스 검증과 실제 Minecraft 동작을 구분해서 기록합니다. 실제 Minecraft 검증 대상은 Docker `minecraft-laya-validation`, `127.0.0.1:25566`, Java 1.21.1입니다.

## 자동 검사

- 일반 테스트 413개 통과. 실제 연결 테스트는 아래 실행 범위와 별도로 기록합니다.
- strict TypeScript 검사와 서버·Vite React 빌드.
- 계약, 목표 분해·배정·예약·실제 결과 확인, 최대 5회 재시도, 오래된 메시지 차단, 재시작 복원 검증.
- 0·1·5·20개의 가상 워커로 동적 등록과 중복 실행 방지 확인.
- HTTP/SSE·SQLite·프로세스 감독·명령 중복 방지와 실제 적용 확인.
- Playwright 시나리오 20개: 목표 미리보기·수정, 하나의 viewer 전환, 오래된 관측 표시, 빈 마을·설정, 모바일 조작, 유휴 연결, 긴 활동 기록, 건축·수확 입력, HTTP 환경에서 viewer 재연결, 주변 건설 부지·고정 좌표 검증, 유휴 봇의 작업 대기 사유, 실제 부지 정리 진행과 건축 단계 구분, 설계도 저장·수정·삭제와 실제 적용 확인·목표 선택, 기본 설계 보호와 잘못된 크기 입력. 인벤토리 슬롯·장비·묶음·핫바·도구 상세와 실시간 이동, 미관측·빈 슬롯·지난 관측 구분, 320·375px 모바일의 9열 배치와 상세 표시를 포함합니다. 사망 위치·실제 부분 회수·미회수, 안전 복구 게이트와 보존된 목표 표시도 확인합니다. 창고의 실제 건설 단계·자재 조건·상자 확인과 오래된 시도 배제도 포함합니다.
- 주변 부지 탐색의 실제 블록·접근 증거 검증, 같은 목표의 건설 단계 전환, 건축 조건 대기의 실제 변화에 따른 재개. 기본 탐색은 제한된 자연 지형 정리 계획을 먼저 평가하고, 계획이 없으면 부지 접근을 최대 2회·총 10초로 제한합니다. 진행 중인 20초 이동을 포함하면 약 30초 이내에 대기로 전환합니다. `allowPreparation: false`인 탐색 전용 목표는 기존 8회·60초 제한을 사용합니다.
- 지형 정리 계획의 실제 변경 전 관측, 시설·작물·액체·중력 블록 보존, 빈 동굴·미관측 지반 거부, 봇 발판 보호, 변경 수량과 접근로 범위 제한. 중단 뒤 실제 변경 결과로 남은 부분을 재개하며, 채운 흙의 자연 잔디 재성장을 허용합니다. 준비 결과를 검증한 뒤에도 건축 목표는 별도의 설계도 완료 관측을 요구합니다.
- 사용자 설계의 크기·재료·가구 검증과 미리보기, 기본 설계 복제 시 동일 배치 보존, 설계도 API와 저장·재시작 복원. 수정·삭제 후 기존 목표의 고정한 버전 유지, 관측에 첨부한 다른 정의 거부와 모델이 반환한 임의 배치 차단을 검사합니다.
- 인벤토리의 실제 46개 슬롯과 분리된 묶음, 선택한 핫바, 방어구·보조 손·제작 슬롯 검증. 열린 상자의 플레이어 영역만 반영하고 비워진 칸과 커서 상태를 확인합니다. 표시 이름·내구도·마법 부여를 공개 아이템 정보에서 읽고, 슬롯 미관측과 빈 인벤토리를 구분합니다.
- 빈 인벤토리에서 관측된 참나무·자작나무를 골라 작업대와 곡괭이를 준비하는 회귀 검사. Java 26.1의 실제 전체 목재 레시피 데이터로도 검사하며, 중간 제작에서 소비한 판자의 보충을 확인합니다.
- 체력·허기가 위급할 때 작업을 배정하거나 재시도를 소모하지 않고, 식량 확보와 실제 체력 회복 뒤 같은 작업을 재개하는 검사. 생존 상태가 이전 건설 대기 사유에 가려지지 않는 UI 검사.
- 체력 6.33·허기 17의 회복 우선권, 실제 체력 20·허기 18 이상까지의 상태 유지, 회복 진입과 배정이 겹친 거절의 재시도 보존을 검사합니다. 회복·식량 대기 지문·관측과 소진한 탐색 예산의 엄격 계약·저장·실제 부팅 인자를 확인합니다. 멜론 드롭, 확인한 밀·작업대의 빵 제작, 창고 식량 회수 양쪽 증거, 새 입고 후 대기 해제와 시간 경과로 예산을 재발급하지 않는 것을 검사합니다.
- 자원 접근 실패 뒤 같은 경로 반복을 막고, 공개 경로 탐색 결과와 실제 지형을 확인한 최대 5개 지상 후보로 이동·재관측하는 검사. 원점 기준 반경 48블록, 총 접근 예산, 탐색 권한, 미관측·액체·절벽·시설·발판 보호와 안전한 중단을 확인합니다. 탐색 기록은 작업 체크포인트로 유지하며 시간 경과와 자체 이동으로 소진한 예산을 초기화하지 않습니다.
- 한 위치에서 접근 후보 8개를 소진해도 남은 지상 탐색을 차단하지 않습니다. 새 지상에 실제 도착한 뒤 접근 후보를 다시 확인하며, 이전 형식의 조기 종료 체크포인트는 원점·방문 기록·시간·사용량을 유지해 남은 탐색만 한 번 복구합니다.
- 건축 재료 대기의 원천 자원(조약돌의 경우 돌)과 최대 64개 실제 접근 좌표를 감시합니다. 알려지지 않은 블록을 공기로 바꾸지 않으며, 자원·재고·접근 지형이 바뀌면 남은 작업을 다시 확인합니다. 식량 탐색도 실제 조건이 바뀔 때 재개하고, 일반 허기에서는 중앙 작업에 안전하게 양도하며 위급한 체력·허기는 검사 주기를 기다리지 않고 중단합니다.
- 일반 수집·제작의 고갈한 자원 대기도 중앙의 실제 조건 비교를 적용합니다. 같은 조건에서 5초마다 재배정하지 않으며, 작물의 같은 블록 이름 안에서 바뀌는 공개 `stateId`를 감시합니다. 상태값 미포함·미관측은 이전 실제 값을 유지하고, 탐색 권한이 없어도 관측한 미성숙 작물의 정확한 좌표를 감시합니다.
- 설치된 Mineflayer 4.39.0 소스 무결성 확인. 프로토콜 767의 실제 레시피 패킷 1,290개 해석·재직렬화 확인.
- 실제 장비와 원거리 적의 수적 우세 판단, 엄폐와 높이 차를 포함한 확인된 경로, 이동 중 체력 변화에 따른 중단, 정확한 적 ID만 인정하는 지원 완료와 유효 시간·최대 재시도 제한을 확인합니다. 바쁜 지원 봇의 대기 중인 규칙은 안전 중단 후 적용하며 최신 적용 확인 전에는 지원을 배정하지 않습니다.
- 유휴·전투·건설 중 사망, 이전 생명의 비동기 동작 정리, 새 생명의 준비·안전 확인, 여러 실제 드롭 묶음과 인벤토리 증가 확인, 부분·미회수 및 재시작 후 회수 예산 보존을 검사합니다.
- 고정 건축 입구의 접근 실패 후 읽기 전용 계획, 현재 시도 관측 검증과 별도 선행 작업 예약, 얕은 자연 지형만 변경, 실제 입구 도착과 건물 완료의 구분, 중단·재시작 후 원래 목표 복귀를 검사합니다.

- 창고 없는 수집의 실제 인벤토리 합산, 기존 10개에서 부족한 22개 배정, 세 봇에 8·8·6개로 분배한 수량의 중복 방지, 추가·유지 목표와 가득 찬 가방·오래된 세션을 검사합니다. 기존 창고 미설정 대기 목표의 ID·입력·세대 유지와 완료 증거의 재시작 복원을 확인합니다. UI에서 창고 없는 목표를 그대로 등록하고 완료 기준과 보존된 수량을 표시하는 검사도 포함합니다.

- 창고 목표의 기본 주변 부지 탐색, 현재 시도의 전체 건물·실제 상자 관측, 공동 창고 자동 등록과 기존 설정 보존, 창고 없는 사용자 설계와 미계획 목표 복원을 검사합니다. 완료한 건설 영역은 로그 정리와 재시작 이후에도 자원 채굴에서 보호합니다. 완료한 일회성 목표의 취소 요청은 상태·세대·증거와 보호 영역을 유지하며, 진행 중인 유지 목표는 기존대로 안전 중단 후 취소합니다.
- 작은 건물의 실제 슬롯 여유를 확인한 지상 재료 준비, 실제 남은 설계의 최대 16개 배치, 문·침대의 두 칸 생성, 부분 재고와 소진한 탐색 예산 보존, 불확실한 제작·취소의 중단을 검사합니다. 실제 26.1의 전체 레시피 데이터로 빈 인벤토리에서 유리판 제작 경로를 검증하고, 원료가 없을 때의 정확한 대기와 계산 한도·순환·깊이 제한도 확인합니다.
- 실제 warehouse 136칸 배치에서 높이 1칸의 내부 상자에 지상으로 접근하는 공통 기준을 검사합니다. 상자 관측·등록·입출고의 접근 반경을 3으로 통일하고, 도착 후 실제 상자·상호작용 거리·취소를 확인합니다. 입출고 양쪽 수량 증거와 거리 초과·상자 변경·취소 시 미실행을 검사합니다.

자동 UI 시나리오는 테스트용 API를 사용합니다. 가상 20봇 검증으로 실제 20봇의 성능이나 Minecraft 서버 용량을 보장하지 않습니다.

## 실제 연결

실제 실행 검증은 별도 테스트 구역에서 재료·지형·성숙한 작물·동물을 준비해 수행합니다. 전체 생존 월드에서 재료 없이 시작하는 자율 발전 검증과는 범위가 다릅니다.

| 대상 | 확인 기준 |
| --- | --- |
| 수집·입고 | 창고 원목 10개에서 부족한 22개를 실제 수집·입고해 총 32개 확인 |
| 창고 없는 수집 | HTTP 목표→실제 fork 워커가 기존 원목 10개에서 22개만 채집해 인벤토리 총 32개와 완료 확인. 보관 작업 없이 완료하고 실제 소비 후 31개로 줄어도 완료 상태·저장된 수량 증거와 SQLite 기록 유지 |
| 제작 | 원목 2개로 판자 8개를 제작하고 실제 인벤토리 수량 확인 |
| 빈 인벤토리 준비 | 원목 3개를 실제 채굴·회수해 작업대와 나무 곡괭이를 만들고, 원래 돌 위치로 돌아가 조약돌 1개 채굴·획득 확인 |
| 자원·식량 복구 | 가까운 매몰 돌을 보존하고 실제 탐색 이동 후 fixture가 새로 노출한 원점에서 44블록 거리의 돌을 관측·채굴해 조약돌 1개 획득. 체력 5에서 같은 탐색으로 성숙 감자 5개 수확 후 실제 섭취로 감자 5→4개·허기 7→8 확인 |
| 저체력 회복·재시작 | 실제 피해로 체력 6.33·허기 17에서 시작해 식량 대기 동안 일반 작업·재시도 0회 확인. 빈 인벤토리와 소진한 탐색 기록을 1차 재시작 후 보존. 실제 멜론 블록을 관측·채집해 식용 드롭을 먹고 허기 회복 확인. 자연 회복으로 체력이 10을 넘은 상태에서 2차 재시작해 회복 우선권 유지. 최종 체력 20·허기 19 뒤 같은 귀환 목표 완료. 음식 지급 0개, `health-recovery.live.test.ts` 1/1 통과(118초) |
| 부지 정리 | 빈 인벤토리로 갇힌 발판에서 시작해 자연 지형 24곳을 깎고 얻은 흙으로 20곳을 메움. warehouse 기초·전체 빈 공간·출입로, 원래 발판 보존과 실제 입구 도착 확인 |
| 농사 | 물·경작·씨앗 설치, 성숙 작물 수확·재심기와 실제 창고 입고 확인 |
| 건축 | cabin 설계의 실제 블록과 가구 상태 확인; 주변 지면에서 부지 탐색 후 warehouse 136개 블록과 가구 상태, 건물 밖 지면으로 종료 확인 |

## 모델과 지원 범위

기존 Laya `/api/decide` 연동 검증은 실제 응답으로 실행 가능한 후보 선택을 확인한 범위였습니다. 이후 수행한 Qwen 가중치 학습·평가·제한된 운영 적용 결과는 아래 2026-10-16 기록과 `training/README.md`에 구분해 남깁니다. 응답 검증 실패나 시간 초과에는 코드 판단을 사용합니다.

건축의 실제 실행 검증은 cabin, warehouse와 cabin을 복제한 6×5×3 사용자 설계에 한정합니다. 기존 warehouse와 사용자 설계도 검증은 건축 재료를 준비한 fixture에서 수행했습니다. 이번 warehouse 전체 검증은 시작 인벤토리를 비우고 도구·건설 재료 지급 없이 실제 원천 자원의 채집·제작부터 완공·창고 연결·후속 입고까지 통과했습니다. 평탄한 주간 구역에 풀과 원목·돌·모래·석탄 블록을 준비하고 최초 체력·허기를 회복한 조건이며, 임의의 생존 지형이나 자유로운 야간 위협 속의 완공 성능 검증은 아닙니다. 별도의 빈 인벤토리 준비 검증은 원목 3개와 돌을 배치한 fixture에서 수행했습니다. 부지 정리는 별도의 울퉁불퉁한 흙·잔디 지형에서 도구와 재료 없이 시작해 실제 44개 변경과 전체 부지를 확인했습니다. 나머지 내장 설계는 구조·재료·완료 조건을 코드로 검사합니다. 자연 지형 정리는 최대 192개 변경과 확인된 얕은 지반을 대상으로 합니다. 자유형 설계 생성, 깊은 굴착·액체·중력 지형 정리와 실제 다수 봇 부하 검증은 추가 작업입니다.

자원 복구 변경에서는 `resource-recovery`, `empty-inventory`, `terrain` 실제 연결 테스트 3개를 다시 실행했습니다. 새 자원·식량 복구 fixture는 실제로 걸은 뒤 별도 자원을 노출하며, 클라이언트의 청크 캐시나 라이브러리 메서드를 바꾸지 않습니다. 기존부터 미관측이었던 청크를 로드한 검증으로 해석하지 않습니다. 노출된 자원의 실제 채집·섭취와 관측 증거를 확인한 범위이며, 임의 생존 지형에서 전체 목표를 완수하는 성능 검증은 아닙니다.
